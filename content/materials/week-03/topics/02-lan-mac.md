# 2. LAN, Ethernet 프레임, MAC

요약: IP는 최종 목적지를, Ethernet 프레임의 MAC은 현재 링크에서 받을 상대를 가리킨다. VM의 가상 NIC에서는 자신의 가상 링크만 관찰할 수 있다.

## 링크에서 누가 받는가

**LAN**은 가까운 범위의 장치가 링크로 연결된 망이고, **WAN**은 떨어진 망을 잇는 넓은 망이다. 케이블이나 무선은 연결 수단이다. **스위치**는 같은 Ethernet 구간에서 프레임을 적절한 포트로 전달하고, **라우터**는 IP 경로를 따라 망 사이의 패킷을 넘긴다. 무선 **AP**는 무선 단말이 망에 붙는 접점이다. 실제 아올다 VM에서 어떤 물리 스위치나 AP를 거치는지는 현재 자료로 확정하지 않는다.

Ethernet을 쓰는 구간에서 호스트는 IP 패킷을 **Ethernet 프레임**에 담아 보낸다. 프레임 머리에는 출발지·목적지 **MAC 주소**가 있다. MAC은 보통 `02:00:00:00:00:0a`처럼 6바이트를 16진수로 적는다. 아래 주소와 구성은 모두 **설명용 예시**다. 실제 VM에서 수집한 패킷이 아니다.

```text
같은 링크라는 가정
A: IP 192.0.2.10, MAC 02:00:00:00:00:0a
       | Ethernet frame: dst MAC 02:00:00:00:00:0b
    [switch]
       |
B: IP 192.0.2.20, MAC 02:00:00:00:00:0b
IP packet inside: dst IP 192.0.2.20
```

스위치는 보통 프레임의 목적지 MAC을 보고 현재 구간의 전달 방향을 정한다. IP 목적지가 알려져 있어도 프레임의 목적지 MAC 칸을 비워 둔 채 Ethernet으로 보낼 수는 없다. “IP는 여정의 끝, MAC은 이번 링크의 받는 이웃”이라는 구분이 핵심이다. 다른 링크로 넘어갈 때 프레임 주소는 새 링크에 맞게 달라질 수 있다.

Linux VM의 가상 NIC도 자기에게 제공된 가상 링크의 프레임을 송수신할 수 있다. 그렇다고 물리 호스트의 전체 패브릭, 다른 VM의 모든 패킷, PC의 무선 구간이 보인다는 뜻은 아니다. 캡처 위치와 권한에 따라 보이는 범위가 달라진다. 반면 1주차 `lo`는 같은 호스트 안의 루프백 경로이므로 Ethernet ARP를 기대할 곳이 아니다.

### 같은 Wi-Fi끼리도 공유기를 거치는데, 왜 직접 전달일까?

집 공유기 한 상자에는 AP·스위치·라우터 등의 기능이 함께 들어갈 수 있다. ‘직접’은 중간 상자를 하나도 거치지 않는다는 뜻이 아니라, **다른 IP 망으로 넘겨줄 게이트웨이를 다음 홉으로 고르지 않는다**는 뜻이다.

| 설명용 상황 | IP 경로와 첫 프레임 |
| --- | --- |
| A와 B가 같은 IP 서브넷·같은 L2 구역이고 직접 연결 경로를 선택 | AP·브리지·스위칭 기능을 통해 전달될 수 있다. Ethernet 쪽에서 IP 패킷을 담은 프레임의 목적 MAC은 B의 것이다 |
| A가 다른 망 D로 보내며 게이트웨이 경로를 선택 | Ethernet 쪽 첫 프레임의 목적 MAC은 게이트웨이의 것이다. NAT 없는 모형에서 안쪽 IP 목적지는 D다 |

같은 Wi-Fi 이름이나 같은 주소 범위만으로 위 첫 조건이 성립하지는 않는다. 클라이언트 격리·VLAN·방화벽 설정으로 서로 통신하지 못할 수도 있다. 무선 구간의 802.11 프레임은 Ethernet과 주소 형식이 다르므로 이 표를 Wi-Fi 캡처의 모든 주소 칸에 그대로 적용하지 않는다. VM의 Ethernet NIC에서 보이는 범위와 PC의 무선 구간을 구분한다. [2주차의 ‘같은 망’ 비교](../../week-02/CONCEPTS.md#same-network) · [9주차 VLAN](../../week-09/CONCEPTS.md) · [12주차 무선](../../week-12/CONCEPTS.md).
