# 주소는 같은데, 망도 같을까?

요약: IPv4 주소와 접두사로 같은 서브넷을 계산하고 Linux 경로와 비교한다. /24·/26의 범위와 게이트웨이를 익히며, 주소 계산과 실제 통신 성공을 구별하는 2주차 교재다.

핵심 개념과 헷갈리는 부분을 다시 볼 때는 [이번 주 핵심 정리](ESSENTIALS.md)를 사용한다. CIDR·경로·도달성을 구별한 뒤 공동 질문의 조건을 바꿔 다시 설명해 본다.

## 1. 지난주 요청에서 주소만 꺼내 보기

지난주에는 `http://127.0.0.1:8080/echo`로 요청했다. `127.0.0.1`은 어느 호스트로 보낼지, `8080`은 그 호스트의 어느 프로그램으로 보낼지를 가리켰다. 이번 주에는 포트를 잠시 내려놓고 묻는다. **내가 이 IP로 보내려면 어느 인터페이스로 나가야 할까?**

먼저 예상해 보자. A가 `192.0.2.10`, B가 `192.0.2.70`이면 같은 망일까? 주소 앞 세 묶음이 같다는 이유만으로 답을 정할 수 있을까? **접두사 길이**를 알아야 각 호스트가 보는 서브넷 범위를 계산할 수 있다. 그다음 실제 어느 인터페이스·다음 홉으로 보낼지는 경로 설정을 확인한다.

본문의 `192.0.2.0/24`는 문서 예시용 주소다. 아올다의 실제 IP가 아니며, 예시 목적지로 외부 통신을 시도하라는 뜻도 아니다. [RFC 5737 §3](https://www.rfc-editor.org/rfc/rfc5737#section-3)에 근거한다.

**이번 주 읽는 순서:** 내 주소 확인 → 주소 종류 → 비트와 CIDR → 범위 계산 → 경로 판단 → 마스크 한 조건 변경. 혼자 교재 전체를 읽는다면 약 25~30분이 걸린다. 공동 탐구에서는 [함께 찾아보기](ARTICLE_LESSON.md)의 두 공식 자료와 필요한 교재 절을 선택해 읽는다. 필요한 개념을 읽은 뒤 주소 카드와 자기 VM의 경로를 설명해 본다. 계산이 막히면 예제 두 개에 시간을 더 쓴다.

## 2. IP는 인터페이스에 붙는다

인터페이스는 운영체제가 통신을 주고받는 접점이다. 물리 NIC나 VM의 가상 NIC에 대응하기도 하고, `lo`나 VPN처럼 소프트웨어로 만든 인터페이스도 있다. 한 호스트에 여러 인터페이스와 여러 주소가 있을 수 있으므로 “컴퓨터 하나에 IP 하나”로 외우지 않는다.

아래는 **설명용 출력이며 실측이 아니다.** 실제 인터페이스 이름은 `eth0`, `ens3` 등 환경마다 다르다.

```text
$ ip -br -4 addr
lo       UNKNOWN    127.0.0.1/8
ens3     UP         192.0.2.10/24
```

| 읽을 자리 | 뜻 | 지금 확인할 것 |
| --- | --- | --- |
| `lo` | 자기 호스트 내부의 루프백 인터페이스 | 지난주 자기 서버 요청과 연결 |
| `ens3` | 이 예시의 가상 NIC에 대응하는 인터페이스 이름 | 내 VM에서는 이름이 무엇인지 |
| `192.0.2.10` | 이 인터페이스의 IPv4 주소 | 실제 출력에서 직접 기록 |
| `/24` | 앞 24비트를 네트워크 부분으로 보는 접두사 길이 | IP와 붙여서 기록 |
| `UP` | 인터페이스의 상태 정보 | 이것만으로 인터넷·HTTP 성공을 결론내리지 않기 |

`lo`의 `UNKNOWN` 표시는 루프백 고장의 증거가 아니다. 인터페이스 상태, 경로 존재, 상대의 응답은 서로 다른 관찰이다. 실제 조회 명령과 출력 보관은 [Linux 안내](../../labs/week-02/LINUX.md)를 따른다.

**말로 확인:** SSH로 들어간 VM에서 `127.0.0.1`은 개인 노트북일까, VM 자신일까? 지난주 curl을 실행했던 위치를 기준으로 설명한다.

## 3. 사설·공인·루프백을 구별하기

사설 주소는 여러 조직이 내부에서 반복해 쓸 수 있도록 예약된 주소다. [RFC 1918 §3](https://www.rfc-editor.org/rfc/rfc1918#section-3)의 세 범위는 다음과 같다.

| 범위 | CIDR | 경계 확인 |
| --- | --- | --- |
| 10.0.0.0 ~ 10.255.255.255 | `10.0.0.0/8` | 10으로 시작하는 범위 |
| 172.16.0.0 ~ 172.31.255.255 | `172.16.0.0/12` | 172 전체가 아님. 172.32.0.1은 밖 |
| 192.168.0.0 ~ 192.168.255.255 | `192.168.0.0/16` | 192 전체가 아님 |

공인 주소는 인터넷에서 전역적으로 쓰이는 주소 체계에 속한다. 그러나 주소를 가졌다는 사실만으로 외부에서 내 서버로 들어올 수 있지는 않다. 실제 경로, 방화벽·보안 그룹, 프로그램의 대기 주소·포트를 함께 확인해야 한다. 사설 주소의 인터넷 접속도 NAT 같은 별도 구성에 달려 있으며, 원리는 11주차에서 다룬다.

`127.0.0.0/8`은 루프백 범위다. `127.0.0.1`은 그중 흔히 쓰는 주소이며 RFC 1918 사설 대역과는 역할이 다르다. `192.0.2.0/24`는 문서 예시용이고 `169.254.0.0/16`은 링크 로컬이다. **RFC 1918에 없으면 무조건 공인 주소**라는 이분법은 틀린다. [IANA 특수 목적 IPv4 등록부](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml)에서 구분을 확인할 수 있다.

이번 주에는 특수 주소 전체를 암기하지 않는다. 내 VM의 주소가 어느 범위에 속하는지와, 그것으로 무엇까지 말할 수 있는지만 설명한다.

**원문으로 확인:** [Public vs Private Addresses 질문](ARTICLE_LESSON.md#2-사설-주소가-아니면-공인-주소일까)에서 필요한 주소 범위를 선택 확인한다. 집 공유기 사례를 내 VM 설정으로 옮기기 전에 실제 주소·경로를 따로 확인한다.

## 4. /24와 /26은 어디에 선을 긋는가

**CIDR(Classless Inter-Domain Routing)은 옛 A·B·C 클래스의 고정 경계 대신 접두사 길이로 주소 블록을 나타낸다.** 지금 주소를 계산할 때 “10으로 시작하니 무조건 /8”처럼 마스크를 추측하지 않는다. 실제로 주어진 주소와 접두사를 함께 읽는다.

IPv4는 32비트이고, 우리가 읽는 네 개의 숫자는 8비트씩을 십진수로 표현한 것이다. 각 묶음은 0~255다. CIDR의 `/n`은 앞에서부터 네트워크 부분으로 사용하는 비트 수다. `/26`은 `/24`보다 네트워크 부분이 2비트 길고, 개별 주소를 구분할 부분은 2비트 짧다.

```text
주소 192.0.2.70 = 11000000.00000000.00000010.01000110
/24 마스크       11111111.11111111.11111111.00000000
                └───────── 앞 24비트 ─────────┘ 8비트
/26 마스크       11111111.11111111.11111111.11000000
                └─────────── 앞 26비트 ──────────┘ 6비트
```

마스크에서 1인 자리는 네트워크 부분을 남기고, 0인 자리는 지운다. 주소와 마스크를 비트별 AND하면 네트워크 주소가 된다. AND는 두 비트가 모두 1일 때만 1이다. [RFC 4632 §3.1](https://www.rfc-editor.org/rfc/rfc4632#section-3.1)은 접두사 표기와 주소 블록 크기를 설명한다.

| 접두사 | 마스크 | 주소 전체 개수 | 이 교재의 일반적인 서브넷에서 호스트에 할당할 수 있는 개수 |
| --- | --- | --- | --- |
| `/24` | `255.255.255.0` | 2⁸ = 256 | 254 |
| `/26` | `255.255.255.192` | 2⁶ = 64 | 62 |

일반적인 `/24`·`/26` 서브넷에서 맨 앞은 네트워크 주소, 맨 뒤는 브로드캐스트 주소라 호스트에 할당하지 않는다. `2^(32−n)−2`를 모든 접두사에 적용하지는 않는다. `/31` 점대점과 `/32`는 별도이며 선택 탐구로 남긴다. 클라우드 플랫폼이 일부 주소를 추가로 예약하면 실제 할당 가능 수는 더 작을 수 있다.

**먼저 예상:** `/24`를 `/26`으로 바꾸면 주소 범위는 넓어질까, 좁아질까? 컴퓨터 수를 센 뒤 답을 읽는다.

**원문으로 확인:** [Subnet Masks 질문](ARTICLE_LESSON.md#3-24와-26은-어느-비트를-남길까)의 `/25` 예시에서 마스크와 접두사의 관계만 확인한 뒤 이 교재의 `/24`·`/26`을 직접 계산한다.

## 5. 두 예제로 범위 직접 구하기

### 예제 A — 192.0.2.70/24

앞 24비트, 즉 앞 세 묶음이 네트워크 부분이다. 마지막 묶음 8비트를 모두 0으로 하면 `192.0.2.0`, 모두 1로 하면 `192.0.2.255`다.

- 네트워크: `192.0.2.0/24`
- 브로드캐스트: `192.0.2.255`
- 일반 호스트 범위: `192.0.2.1` ~ `192.0.2.254`
- `.10`과 `.70`은 이 `/24` 범위에 함께 들어간다.

### 예제 B — 192.0.2.70/26

마지막 묶음에서 네트워크 비트가 두 개 더 생긴다. 블록 크기는 64이므로 0, 64, 128, 192에서 각각 시작한다. **70은 64 이상, 128 미만**이므로 두 번째 블록이다.

```text
70의 마지막 8비트    01000110
192의 마지막 8비트   11000000   ← /26 마스크의 마지막 묶음
AND 결과             01000000 = 64
```

| 네트워크 | 전체 마지막 묶음 | 일반 호스트 마지막 묶음 | 브로드캐스트 마지막 묶음 |
| --- | --- | --- | --- |
| `192.0.2.0/26` | 0~63 | 1~62 | 63 |
| `192.0.2.64/26` | 64~127 | 65~126 | 127 |
| `192.0.2.128/26` | 128~191 | 129~190 | 191 |
| `192.0.2.192/26` | 192~255 | 193~254 | 255 |

`.70/26`의 네트워크는 `.64/26`, 브로드캐스트는 `.127`이다. `.10/26`은 `.0/26`에 속하므로 서로 다른 서브넷이다. 외울 것은 “끝자리가 0이면 네트워크”가 아니라 **주어진 접두사로 경계를 계산하는 방법**이다. 경계가 마지막 묶음에 있지 않아도 같은 방법을 쓴다. 예를 들어 `/20`은 세 번째 묶음의 앞 4비트를 남기므로 그 묶음의 블록 크기가 16이다.

## 6. 같은 서브넷 계산 다음에는 경로를 읽는다

단순한 한 인터페이스 환경에서 연결된 서브넷 목적지는 해당 링크로 보낸다. 다른 망의 목적지는 그 망으로 가는 경로가 필요하고, 흔히 게이트웨이가 다음 전달 상대가 된다. 경로표의 `default`는 모든 IPv4 주소에 맞는 `0.0.0.0/0`을 뜻한다. 더 구체적인 경로가 없을 때 사용하는 후보이지 모든 패킷이 반드시 지나는 길이 아니다.

아래는 **설명용 출력**이다. `via`는 다음 홉, `dev`는 나갈 인터페이스, `src`는 선택된 출발지 주소를 읽는 단서다.

```text
$ ip -4 route
default via 192.0.2.1 dev ens3
192.0.2.0/24 dev ens3 proto kernel scope link src 192.0.2.10
```

```text
내 VM (.10/24) ── ens3 ── 같은 링크의 상대 (.70/24)
                      └─ 게이트웨이 (.1) ── 다른 망
```

이 그림은 기본 모델이다. 아올다 실제 토폴로지나 NAT 배치를 확인한 결과가 아니다. 다중 인터페이스·정책 라우팅·더 구체적인 호스트 경로 등이 있으면 주소의 모양만 보고 실제 경로를 단정할 수 없다. 이 주에는 구성을 바꾸기보다 `ip -4 route get 목적지`로 커널이 고르는 경로를 확인한다. 이 명령은 경로 조회이며 ping처럼 상대 응답을 검사하지 않는다. [iproute2의 ip-route 설명](https://git.kernel.org/pub/scm/network/iproute2/iproute2.git/tree/man/man8/ip-route.8)을 참고했다.

**원문으로 확인:** [CIDR 질문](ARTICLE_LESSON.md#4-cidr-표기만으로-다음-홉이-정해질까)의 지정 절에서 접두사 표기와 자기 VM의 현재 경로표를 구분한다.

**틀린 설명 고치기:** “같은 서브넷이고 인터페이스가 UP이니 HTTP도 성공한다.” 상대 상태·연결된 링크·중복 주소·정책·대기 중인 프로그램 중 무엇을 더 확인할지 말해 본다.

아래는 **주소·경로를 새로 만든 설명용 출력**이다. 실행하거나 VM에 설정하는 값이 아니다. 기본 경로와 직접 연결 경로에, 주소 하나로 가는 경로가 더해졌다고 하자.

~~~text
default via 192.0.2.1 dev ens3 proto dhcp src 192.0.2.10 metric 100
192.0.2.0/24 dev ens3 proto kernel scope link src 192.0.2.10 metric 100
192.0.2.1 dev ens3 proto dhcp scope link src 192.0.2.10 metric 100
192.0.2.3 dev ens3 proto dhcp scope link src 192.0.2.10 metric 100
198.51.100.80 via 192.0.2.3 dev ens3 proto dhcp src 192.0.2.10 metric 100
~~~

| 읽을 부분 | 이 예제에서 뜻하는 것 |
| --- | --- |
| 목적지 뒤에 접두사가 없는 한 주소 | IPv4 경로표에서는 해당 주소 하나를 지정한 호스트 경로인 `/32`로 읽는다. 내 인터페이스에 붙은 주소라는 뜻은 아니다 |
| `proto kernel` / `proto dhcp` | 주소 설정에 따라 커널이 만든 경로 / DHCP로 받은 정보를 바탕으로 설치된 경로. 전송할 패킷의 프로토콜 이름이 아니다 |
| `scope link` | 이 경로는 해당 링크로 직접 전달하도록 설정돼 있다. 상대의 실제 응답까지 확인한 것은 아니다 |
| `metric 100` | 비교 가능한 경로 후보 사이의 우선순위 값. 작은 값을 선호하지만 이것만 보고 전체 경로표에서 한 줄을 고르지 않는다 |

같은 라우팅 테이블 안에서 목적지에 맞는 경로 중 **접두사가 가장 긴 것**을 먼저 고른다. 따라서 이 예제의 `198.51.100.80`은 기본 경로의 `.1`이 아니라, 주소 하나에 맞는 경로의 `.3`을 다음 홉으로 고른다. `192.0.2.3 ... scope link`는 `.3` 자체로 직접 전달하도록 설정한 경로이고, `198.51.100.80 via 192.0.2.3`은 다른 목적지로 갈 때 `.3`을 거치도록 설정한 경로다. 여기서는 `/24` 연결 경로도 `.3`을 포함하므로 `.3` 호스트 경로가 항상 필요한 것은 아니다.

이 경로표에서 두 목적지를 조회한 **설명용 결과**를 비교해 보자. 실제 출력의 추가 필드는 환경마다 다르다.

~~~text
$ ip -4 route get 192.0.2.70
192.0.2.70 dev ens3 src 192.0.2.10
$ ip -4 route get 198.51.100.80
198.51.100.80 via 192.0.2.3 dev ens3 src 192.0.2.10
~~~

첫 결과는 이 Ethernet 예제에서 목적지로 직접 전달할 인터페이스를, 둘째는 다음 홉 `.3`을 함께 보여 준다. 표의 위아래 순서로 고르는 것이 아니며, 두 조회 모두 실제 응답을 확인한 것은 아니다. 여러 테이블·정책이 있는 환경은 자신의 `ip -4 route get 목적지` 결과를 읽는다. 상세 원리는 [7주차 경로 교재](../week-07/CONCEPTS.md)로 이어진다.

클라우드 VM에는 metadata 서비스용 추가 경로가 보일 수도 있다. 예를 들어 OpenStack에서 쓰는 `169.254.169.254`는 VM이 자기 설정 정보를 얻는 서비스 주소다. 이 주소가 경로표에 있다는 사실을 DHCP 실패나 인터넷 연결 성공으로 해석하지 않는다. 여기서는 용도만 구별하고 요청을 보내는 실습은 하지 않는다. DHCP 설정은 [5주차](../week-05/CONCEPTS.md), 실제 클라우드 구성은 [13주차](../week-13/CONCEPTS.md)에서 이어 본다. [iproute2 경로 필드](https://git.kernel.org/pub/scm/network/iproute2/iproute2.git/tree/man/man8/ip-route.8) · [OpenStack metadata](https://docs.openstack.org/neutron/latest/admin/intro-os-networking.html#metadata).

</details>

<span id="vpn-address-route"></span>

<details>
<summary>VPN은 켜졌는데 SSH가 안 된다면? — 주소와 경로 구별하기</summary>

Wi-Fi와 WireGuard를 함께 쓰는 PC를 생각해 보자. 다음은 **문서용 주소로 만든 예시**이며 실제 접속 설정이 아니다.

| 구분 | 예시 | 역할 |
| --- | --- | --- |
| Wi-Fi 인터페이스 주소 | `192.0.2.10/24` | 기존 네트워크에서 PC가 쓰는 주소 |
| WireGuard 인터페이스 주소 | `198.51.100.10/32` | 터널 안에서 PC가 쓰는 주소. 갈 수 있는 목적지 전체를 뜻하지 않는다 |
| 접속하려는 VM 주소 | `203.0.113.20` | SSH 요청의 최종 목적지 |
| 상대 Endpoint | `198.51.100.200:51820` | 암호화된 바깥 UDP 패킷을 받는 피어(터널로 통신하는 상대)의 주소·포트 |

이 예제에서 VM으로 가는 경로가 WireGuard 인터페이스를 선택한다면, 안쪽 IP 목적지는 `203.0.113.20`, 바깥 IP 목적지는 Endpoint의 `198.51.100.200`이다. 바깥 패킷은 기존 Wi-Fi 연결을 통해 상대에게 간다. **VPN 인터페이스가 하나 늘어도 독립적인 물리 회선이 추가된 것은 아니다.**

`AllowedIPs`는 송신할 때 목적지에 맞는 **피어**를 고르고, 수신할 때 그 피어가 보낸 안쪽 패킷의 **출발지 주소**를 검사하는 데 쓰인다. 운영체제가 먼저 패킷을 WireGuard 인터페이스로 보내도록 경로가 설정돼 있어야 한다. `wg-quick`처럼 AllowedIPs에서 OS 경로도 만드는 도구가 있지만, 경로 설치 방식은 실행 도구와 설정에 따라 다르다. AllowedIPs를 바꾸는 것만으로 경로·피어·방화벽·반환 경로·SSH 서비스가 모두 정상이라고 할 수는 없다. [WireGuard 공식 설명](https://www.wireguard.com/#cryptokey-routing) · [wg-quick(8)](https://git.zx2c4.com/wireguard-tools/about/src/man/wg-quick.8).

VPN 인터페이스 주소가 보여도 VM 목적지 경로가 Wi-Fi 기본 경로를 선택할 수 있다. **주소 추가 → 목적지 경로 → 피어와의 암호화 통신 → VM의 SSH 응답**은 각각 다른 확인이다. 터널로 보내는 목적지를 제한한 구성에서는 모든 인터넷 트래픽이 VPN을 지나지도 않는다. 주소는 프로필 등에 미리 설정할 수 있으며, WireGuard 서버가 반드시 자동 배정하는 것은 아니다.

Windows에서 선택 비교를 한다면 **PC의 PowerShell**에서 `Get-NetIPAddress -AddressFamily IPv4`로 주소를, `Find-NetRoute -RemoteIPAddress "허용된_VM_IPv4"`로 선택된 출발지 주소와 경로를 조회한다. 자리 표시자를 본인의 허용된 주소로 바꾸며 설정은 변경하지 않는다. **SSH 안의 Linux 명령은 VM의 경로를 읽는다.** PC·WSL·VM의 출력을 섞지 않는다. 이 비교는 기존 Linux P1을 대체하지 않는다. [Find-NetRoute 공식 설명](https://learn.microsoft.com/en-us/powershell/module/nettcpip/find-netroute).

`Find-NetRoute`는 주소 객체와 경로 객체를 반환한다. 앞의 `IPAddress`는 선택한 출발지 주소이고, 뒤의 `DestinationPrefix`와 `InterfaceAlias`는 일치한 목적지 경로와 인터페이스다. 주소 객체의 `PrefixLength`를 목적지 경로로 읽지 않는다. 아래는 **두 경우 모두 WireGuard 주소가 존재한다고 가정한 비교 표**이며 명령의 실측 출력은 아니다.

| 읽을 값 | VM 목적지 경로가 Wi-Fi를 고른 경우 | VM 목적지 경로가 WireGuard를 고른 경우 |
| --- | --- | --- |
| 출발지 `IPAddress` | `192.0.2.10` | `198.51.100.10` |
| 경로의 `DestinationPrefix` | `0.0.0.0/0` | `203.0.113.20/32` |
| 경로의 `InterfaceAlias` | Wi-Fi | WireGuard |

두 경우의 차이는 인터페이스 주소의 유무가 아니라 **VM 목적지에 대해 선택한 경로**다. 오른쪽도 암호화 통신이나 SSH 응답까지 보장하지는 않는다. 실제 인터페이스 이름과 값은 환경마다 다르다.

**SSH에 적은 주소가 VM의 `ip addr`에는 없다면?** OpenStack의 일반적인 Floating IP 구성에서는 외부 네트워크 쪽 주소로 온 패킷을 VM의 네트워크 포트에 할당된 주소(fixed IP)로 변환해 전달할 수 있다. 예를 들어 별도 구성에서 접속에 쓰는 VM 주소 `203.0.113.20`이 VM 내부 인터페이스의 주소 `192.0.2.50`에 대응할 수 있다. Floating IP라는 이름이 반드시 인터넷 공인 주소라는 뜻은 아니다. 실제 주소 대응·변환 위치는 본인 환경의 설정을 봐야 한다. VM에서 보인 출발지 주소가 PC 주소와 다르더라도, 주소 하나만으로 NAT나 중계 장비의 위치를 확정하지 않는다. 응답이 돌아올 경로도 필요하다. [OpenStack 일반 구성](https://docs.openstack.org/neutron/latest/admin/intro-os-networking.html#self-service-networks) · [11주차 NAT](../week-11/CONCEPTS.md) · [13주차 클라우드](../week-13/CONCEPTS.md).

</details>

<details>
<summary>같은 학교망·같은 Wi-Fi·같은 서브넷은 같은 말일까?</summary>

| ‘같다’고 부르는 대상 | 뜻 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 학교·회사 전체 망 | 한 조직이 운영하는 네트워크 | 모든 장치가 같은 서브넷이거나 서로 접근 가능한지 |

| L2 연결 구역 | 프레임·브로드캐스트를 전달하도록 이어진 구역 | 모든 IP 통신과 서비스가 허용되는지 |

우리 집과 친구 집이 모두 `192.168.0.0/24`를 써도 두 집의 링크가 이어진 것은 아니다. 학교에서도 같은 Wi-Fi 이름을 여러 건물에서 제공하면서 서로 다른 서브넷으로 나눌 수 있다. 서로 다른 서브넷 사이의 통신이 학교 내부 라우터를 통해 이뤄질 수도 있어, 반드시 인터넷을 나갔다 오는 것은 아니다. 실제 학교망 구조는 이 예시로 확정하지 않는다.

‘어느 IP 경로를 고르는가’는 이번 주에, ‘그 링크에서 누가 프레임을 받는가’는 [3주차 LAN·MAC](../week-03/lan-mac.html#home-router)을 보며 구별한다. VLAN 구성은 [9주차](../week-09/CONCEPTS.md), AP 관리·로밍은 [12주차](../week-12/CONCEPTS.md)에서 이어 간다.

## 7. 마스크만 다르면 양쪽 판단도 다르다

격리된 두 노드 A와 B가 하나의 가상 링크로 연결되어 있다고 하자. 라우터와 기본 경로는 없다. 다음은 **실험 전 예측**이다. 실제 Linux 실행 결과는 [개인 실습 증거](../../labs/week-02/LINUX.md#개인-실습-증거-보관)로 보관하고, 함께 질문을 설명할 때 필요한 근거를 보여 준다. 추가 메모는 선택이다.

| 조건 | 먼저 풀 질문 | 근거 확인 |
| --- | --- | --- |
| C1 — A `.10/24`, B `.70/24` | 각자 어떤 범위로 묶을까? | P2 손계산 뒤 검산 |
| C2 — A만 `.10/26`, B는 `.70/24` | 두 방향의 판단이 같을까? 경로는 있을까? | 양쪽 범위·주어진 경로 조건 |
| 선택 복구 — A를 `.10/24`로 되돌림 | 원래 상태로 돌아갔다고 무엇으로 확인할까? | 실제 실행했다면 동일 조건 재조회·요청/복구 |

“숫자가 비슷하니 같은 망”이라는 주장에 어떤 정보가 빠졌는지 설명한다. 양쪽 판단과 응답 경로를 나눠 보고, [Subnetting 선택 질문](ARTICLE_LESSON.md#5-같은-서브넷이라면-통신도-성공할까)의 계산·경로 조회·도달 증거를 구분한다. C1/C2의 완성 풀이와 흔한 오답은 [분리 해설](ANSWERS.md#공동-질문-해설)에서 자기 설명 뒤 비교한다.

실제 실험은 [Linux 안내의 격리 실습](../../labs/week-02/LINUX.md)대로 진행자가 사전 점검한 환경에서만 한다. SSH 관리 인터페이스를 바꾸는 과제가 아니다. 준비되지 않았다면 선택 실험을 실행하지 않는다. [제공 출력](../../labs/week-02/SAMPLE_OUTPUT.md)을 읽었다면 제공 분석으로 표시한다. 선택 미실시는 필수 P1/P2의 완료를 막지 않으며 실제 실행/복구를 했다고 쓰지는 않는다.

다음 주에는 “같은 링크로 보내기로 결정한 뒤, 상대의 MAC 주소는 어떻게 알아낼까?”를 ARP·ICMP로 확인한다. 이번 주에 ARP 캐시 초기화나 라우터 구축까지 끝낼 필요는 없다.
